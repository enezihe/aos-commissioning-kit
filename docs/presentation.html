What works today

Runs as a containerkind and OpenShift

The flight service runs as a container image, managed by Helm, on a local kind cluster and on a Red Hat OpenShift cluster, where it is reachable over a public HTTPS route.

EndpointBehaviour
GET /healthLiveness and readiness check used by Kubernetes probes
GET /flightsList flights
POST /flights201 on create, 409 if duplicate, 422 on an invalid body
PATCH /flights/{no}Update the gate, 404 if the flight does not exist

Known limitation: data lives in memory. See the key lesson next.

07

One shared notebook: keep state outside the pod

Observed in Phase 2Stateless vs stateful

Two replicas behind one Service gave different answers to the same request.

What happened

A flight was created through the Service and landed in one pod's memory. Eight identical GET /flights calls from inside the cluster returned the flight 4 times and an empty list 4 times.

Why

Each pod keeps flights in its own memory, like two pizza makers with two separate notebooks. The Service spreads requests across both.

The fix

Move the data out of the pod into a shared database (PostgreSQL), so every replica reads and writes the same notebook.

MeaningOur flight service
StatelessA pod remembers nothing. Copy it as often as needed.What it should be
StatefulStores data. Copying it is hard and needs care.The database

Today the service is meant to be stateless but keeps state in memory, the worst of both worlds. The database is planned for a later phase; Phase 2 stayed focused on deployment mechanics and the flaw is documented on purpose. Scaling to one replica would hide the symptom but remove redundancy.

In an implementation role, naming the cause of a symptom like this ("state is not shared between replicas") is exactly the diagnosis a customer needs.

08

What OpenShift taught us

Phase 3Troubleshooting log

The same Helm chart that worked on kind needed four findings before it ran on OpenShift. Each one is a typical commissioning situation.

1. ImagePullBackOff

The image only existed on the laptop and inside kind. The pod events showed the pull from docker.io failing. Fix: build the image inside the cluster (BuildConfig and ImageStream) and point the chart at the internal registry.

2. Random non-root user

OpenShift ran the image with a random user ID in group 0, although the Dockerfile never asked for it. It worked because the service only reads files. A service that writes files would fail with permission denied.

3. The sandbox sleeps

After a few days the Deployment was scaled to zero and the login token had expired, but the Helm release, build and image survived. Scaling up and logging in again restored the service in minutes because everything lives in code.

4. Route instead of Ingress

A Route exposes the service over HTTPS. It exists only on OpenShift, so the chart creates it only when route.enabled is true.

Same chartkind (values.yaml)OpenShift (values-openshift.yaml)
Image sourceLoaded into the nodeInternal registry, built in the cluster
Public accessPort-forwardHTTPS Route
Chart templatesIdentical in both environments

Not done yet: the Dockerfile still builds a root-oriented image and the Route has no authentication. Hardening is a follow-up.
